## 4c. The artifact cannot name its own revision (blocks all evidence binding)

This is the reason every piece of evidence in this session has needed an artifact-hash caveat. The
C type manifest carries a `commit` field, and it is **always `null`**:

```
$ strings zig-out/lib/libghostty-vt.0.1.0.dylib | grep -o '"library_version":"[^"]*","commit":[^,]*'
"library_version":"0.1.0-dev","commit":null,"dirty":null
```

`src/terminal/c/types.zig:426` writes it from `build_options.version_build`. That option is
`self.version.build` (`src/terminal/build_options.zig:325`), and `src/build/Config.zig` populates
`.build` on the ordinary path (`:352 .build = vsn.short_hash`) and on the no-git path
(`:321 .build = "0000000"`) — but **not** on the tagged-release early return (`:344-349`), which
returns only `major/minor/patch`.

So a build either stamps its commit or silently stamps nothing, depending on which path the version
resolver takes, and a consumer holding the `.dylib` or the wasm module cannot tell which source
produced it.

**Not fixed here, deliberately.** The fix is small — add `.build = vsn.short_hash` to the tagged
early return — but `src/build/Config.zig` also `@panic`s on a tag that is not exactly `vX.Y.Z`
matching `build.zig`, and `GitVersion` returns `""` (not `null`) when `git describe --exact-match`
fails, which is the ordinary untagged case at `abcbf73b`. Reasoning about that under time pressure,
in code that governs **release versioning**, is not worth the risk of getting it wrong.

**Recommended follow-up:** make the commit stamp unconditional on every path, and add a check that a
built artifact's `commit` field is non-null and matches `git rev-parse --short HEAD`. That single
change would remove the "which revision is this artifact?" caveat from every future docket entry.

## 4d. Corrected understanding: the visible failure was not the blocker

Every open PR was red on **Lint & Format** (Trunk Check), and that is what the record has been
treating as the reason nothing merged. It was not. Branch protection on `main` reads:

```
strict: true
required status checks: ['ci / lint', 'ci / test']
```

Two consequences that the red check obscured:

1. **`Lint & Format` is not required.** A Trunk Check failure cannot block a merge.
2. **`strict: true` requires the branch to be up to date with `main`.** Every PR was `BEHIND`. With
   15 open PRs and strict mode, each merge invalidates all the others, so _no_ branch could
   satisfy "up to date" while the queue sat unmerged. That, not formatting, was the blocker.

Verified every open PR already had `ci / lint=SUCCESS` and `ci / test=SUCCESS`, then merged
`origin/main` into all 15 branches — a plain merge, no force-push, no history rewrite. All 13
clean-checkout merges applied without a single conflict, which independently confirms `main` and the
branches had not diverged in content.

**Before:** 7 `BEHIND` (unmergeable), the rest `BEHIND`/`UNSTABLE`.
**After:** **15/15 `MERGEABLE`**, 12 of them `UNSTABLE` purely on the non-required Trunk Check.

**The transferable lesson:** when a required-check configuration is `strict: true`, PR queue health
is a function of _branch freshness_, not of whether optional checks are green. The red check was a
true signal about a real (and separately fixed) defect, and a false signal about why the queue was
stuck. Recorded here because the earlier readings in this file treated the red check as the blocker.
