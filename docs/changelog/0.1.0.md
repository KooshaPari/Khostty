# Khostty 0.1.0

**Release date:** not yet released — this document is written ahead of the tag.
**Version:** `0.1.0` (source value `0.1.0-dev`) · **ABI soname:** `libghostty-vt.0.1.0`
**Upstream base:** Ghostty `1.3.2-dev` @ `d4c88d8069912b653d707191388ca98e24751f12` (2026-09-15)
**Tag that would be created:** `v0.1.0` — **does not exist yet**; see [RELEASE.md](../RELEASE.md).

Khostty is a fork of [Ghostty](https://github.com/ghostty-org/ghostty). Upstream ships
`libghostty-vt` — a standalone C virtual-terminal library, 203 `GHOSTTY_API` functions
across 35 headers, with macOS and Linux/GTK application runtimes. This is the first
release of the fork's own delta.

**Read the Known issues section before using anything here.** Several artifacts are
verified as *build products* and not as *running programs*, and this document says so
per artifact rather than leaving it implied.

---

## 1. What `0.1.0` means

`0.x` means the agent-facing surfaces are **not frozen**. The IPC v1 protocol and the
polyglot bindings may change between `0.1.x` releases. The upstream C ABI under
`include/ghostty/vt/` is inherited and tracks upstream, not this fork's version line.

There is no API freeze, no performance claim, and no general-availability claim for the
Windows or GTK applications. See [RELEASE.md §3](../RELEASE.md) for the full statement.

## 2. What Khostty adds over upstream Ghostty

Four deltas. Each row below states what was added, the gate that produced the evidence,
and what the evidence does *not* cover.

### 2.1 An independent conformance gate (G2)

Upstream's `libghostty-vt` is the same code this fork builds; the contribution is a
**Khostty-owned behavioural gate over it**.

| Item | Detail |
|---|---|
| Harness | `conformance/` — `build.sh`, `harness.c`, per-category case files |
| Corpus | 84 cases across 8 categories |
| Result | **84/84 pass** (recorded 2026-09-17, commit `b2c388c9b`) |

This is the fork's most solid artifact: it answers "did we break the terminal?" with a
number, and it is reusable by a consumer who does not want the rest of the fork.

*Not covered:* the gate is not wired into CI as a required check, and it exercises the
library, not any application runtime.

### 2.2 Windows application runtime (G3)

Upstream has **no** Windows app runtime: `Runtime.default` returns `.none` on Windows.
Khostty adds `src/apprt/windows/` — a native Win32 runtime with DirectWrite rendering,
keyboard and mouse input encoding, clipboard, drag-and-drop, font discovery, theming,
and a named-pipe IPC scaffold.

| Item | Evidence, observed 2026-09-18 |
|---|---|
| Cross-build | `zig build -Dtarget=x86_64-windows-gnu -Dapp-runtime=windows -Demit-macos-app=false` → exit 0 (8m12s) |
| Artifacts | `ghostty.exe` (43,470,336 B), `ghostty-vt.dll` (7,545,344 B), plus `.pdb` and `.lib` files |
| Host-side tests | Isolated `zig build test-windows-apprt -Dtest-filter=apprt` binary run directly → **`All 25 tests passed.`**, exit 0; covers Window, input, keyboard, interface, ipc, mouse, renderer, surface |
| ABI shape | 198 distinct `ghostty_*` exports in the DLL; the 35 headers declare 206 distinct functions (203 `GHOSTTY_API` + 3 `static inline`); **0 exports are undeclared**; the 8-name gap is exactly the 3 `static inline` helpers in `vt/modes.h` and the 5 `__wasm__`-gated `ghostty_wasm_*` allocators |
| Windows installer | **BUILT + install-verified 2026-09-19** on `kooshapari-desk` with Inno Setup 6.7.1: `ISCC.exe khostty.iss` → `Khostty-0.1.0-windows-x86_64-setup.exe` (19,766,307 B, `sha256 4070e89e…095546`); silent install → payload hashes MATCH → installed `ghostty.exe` runs → silent uninstall, 0 residual files |

**The binaries HAVE now been executed (2026-09-19).** `kooshapari-desk` — a Windows
NT 10.0.28120 / AMD64 host, online and designated a compute-mesh runner — was used:
both files were copied there byte-identically (sha256 re-verified) and run.
`ghostty.exe +version` → exit 0, reporting `app runtime: .windows`,
`font engine: .freetype_windows`, `libxev: iocp`, `Zig 0.16.0`, build mode `.Debug`.
`ghostty-vt.dll` was loaded via `LoadLibraryW` and its ABI driven live:
`ghostty_terminal_new(NULL,&t,80,24)` rc 0, `get COLS/ROWS` 80/24, `resize(100,40)` →
100/40, `vt_write` of text + SGR + OSC-0 → `CURSOR_Y` 1 and `TITLE` `Khostty-Win`,
`VT_GROUND` 1, `terminal_free` clean, `ghostty_build_info(SIMD)` rc 0 — **0 failures**.
Evidence: `../sessions/20260916-fork-assessment/evidence/windows_runtime_verify_2026-09-19.txt`, harness

remaining: `.Debug` build, CLI `+version` only (no GUI window). The installer is now compiled and install-verified (see §2.2). See Known issues §4.1.

### 2.3 Agent/IPC surface (G4)

Upstream IPC is a three-action channel (`new_window`, `new_tab`,
`toggle_quick_terminal`), command-line shaped. Khostty adds a v1 agent protocol:
line-delimited JSON over a local socket, 13 commands, pane handles, machine-readable
state, scrollback search, and an async event broker with token auth.

Normative spec: [`src/apprt/ipc/protocol.md`](../../src/apprt/ipc/protocol.md).

**Test evidence, executed while writing this document (2026-09-18):**

```console
$ for f in protocol state events auth pane handler server; do zig test src/apprt/ipc/$f.zig; done
protocol: All 30 tests passed.
state:    All 35 tests passed.
events:   All 43 tests passed.
auth:     All 12 tests passed.
pane:     All 83 tests passed.
handler:  All 121 tests passed.
server:   All 134 tests passed.
# 458 tests total, every module exit 0
```

`server.zig`'s tests bind real Unix sockets, so framing, auth, malformed-frame
rejection, ping round-trip and stale-socket replacement are exercised over the wire,
not against a mock transport.

Those seven figures are **cumulative**: each `zig test <module>` also runs the tests
of every module it imports, so the `server.zig` run reports `handler.test.*`,
`state.test.*` and so on. 458 is the sum of test *executions* across the seven entry
points; **134 distinct tests** are defined across the seven modules, all passing.

**Two honest limits, from the spec's own §7:**

1. **The app-thread hop is not wired yet.** The server is not started from the
   application, so nothing is listening in a running Khostty today. The protocol works
   end to end against a host that implements the `Host` interface (the tests prove
   this); the real runtime's host is not yet reachable from a connection thread.
2. **`pane.focus` and `pane.search` return `host_unsupported` on the real runtime.**
   Upstream has no synchronous "focus surface by id" or "scan scrollback and return"
   entry point. Both are named gaps, not silent no-ops.

The Windows named-pipe transport is a scaffold: every operation returns
`error.Unimplemented`, and the pipe path constant is known to be malformed.

**Do not build against this surface yet.**

### 2.4 Polyglot FFI (G5, G6, G7)

Upstream ships C and Zig APIs with examples in other languages. The fork ships
**safe, packaged wrappers** for four ecosystems, all laid out from the library's own
type manifest (`ghostty_type_json()`) rather than from a hand-written offset table.

| Ecosystem | Package | Gate evidence | Re-verified 2026-09-18 here? |
|---|---|---|---|
| Rust | `khostty-vt` | 199/199 tests (G5) | **yes** — 199/199 pass (195 unit/integration + 4 doc-tests) |
| Go | `khostty-go` | `gofmt`/`go build`/`go vet` clean, 45 tests pass, both examples run | **no — fails at link on this host today**; see Known issues §4.8 |
| Python | `khostty-python` | `ruff` clean, 162 pytest cases pass, both examples run, sdist + wheel built and installed in fresh venvs | **yes** — 162 passed under Python 3.12 |
| WebAssembly / TS | `@khostty/libghostty-vt-wasm` | 54/54 tests, `tsc --strict` with `skipLibCheck: false`, 187 `ghostty_*` exports, 813,670-byte `.wasm` reproduced byte-identically from a cold cache | not re-run (recorded 2026-09-18 in [INSTALL.md](../INSTALL.md)) |

Go + Python total 207 tests, the figure the WBS gate records.

The design contribution worth calling out is the **type manifest**: a hand-written
offset table corrupts memory silently on the next struct change, whereas a manifest
lookup fails loudly. This caught a real defect during development — an undersized
`GhosttyBuffer` missing its `cap` field. Both the Go and Python wrappers validate
their declarations against the linked library at test time.

*Known limitation:* `GHOSTTY_MODS` and `GHOSTTY_KITTY_KEY_FLAGS` are `#define` bitmasks
rather than C enums, so the manifest cannot enumerate their bits. They are transcribed
from the headers and the encoding tests verify them behaviourally instead.

### 2.5 WASM distribution (G7)

`khostty-libghostty-vt-wasm-0.1.0.tar.gz` is a typed ESM package with a `package.json`
`exports` map, TypeScript declarations, and a consolidated 2,102-line C header.
Consumability was verified by installing the tarball into a fresh consumer directory
and importing a bare specifier resolved through the exports map — recorded 2026-09-18
in [INSTALL.md](../INSTALL.md).

*Not covered:* tests are Node-only. The module is freestanding and dependency-free, so
Node exercises the same code path a browser would, but **no browser was ever run**.
Kitty graphics is absent from the WASM build by design (upstream disables it on
freestanding targets), so 16 of the 203 declared functions are not exported.

## 4. Known issues

Stated plainly. Every one of these is a real limitation, not a deferred nicety.

### 4.1 Windows binaries are built, ABI-checked, and now executed on Windows (windowed run still unverified)

`ghostty.exe` and `ghostty-vt.dll` exist, are real PE32+ files, hash reproducibly, and
their exported ABI matches the headers with zero undeclared exports. **They were run on
Windows on 2026-09-19** on `kooshapari-desk` (Windows NT 10.0.28120, AMD64), copied
there byte-identically with sha256 re-verified: `ghostty.exe +version` → exit 0
(`app runtime: .windows`, `font engine: .freetype_windows`, `libxev: iocp`), and
`ghostty-vt.dll` was loaded and driven through its live terminal ABI — create, query,
resize, VT write with SGR + OSC-0 title, and free — **0 failures** (evidence
`../sessions/20260916-fork-assessment/evidence/windows_runtime_verify_2026-09-19.txt`). What remains unverified
is narrower than before: the run used the CLI `+version` action, so **no GUI window was
launched** and rendering, input handling, and the named-pipe transport are still not
exercised on Windows. The artifact is a `.Debug` build. The Windows installer is no
longer a gap: it was compiled with Inno Setup 6.7.1 and install/uninstall-verified on
2026-09-19 (see §2.2). The earlier claim that no Windows host was available
was wrong — a host was reachable over the compute mesh all along.

### 4.2 The macOS `.app` was verified by `codesign` and `--version`, but no GUI session was observed

`dist-release/macos/Khostty-0.1.0-macos.zip` was built, signed, and verified:
`codesign --verify --deep --strict` → *valid on disk* / *satisfies its Designated
Requirement*, and the bundled binary ran non-interactively:
`Contents/MacOS/ghostty --version` → `Ghostty 1.3.2-main-+41b24baad`, exit 0.

**The bundle was never launched in a GUI session**, and it is **not notarized**. A
Developer ID Application identity is present and was used to sign it; what is absent
are `notarytool` credentials, so the bundle was never submitted to Apple. Its own
evidence file records `launch_verified: NO`. On another machine, Gatekeeper will
warn or block until the user overrides it. No window has been observed opening.

### 4.3 The GTK Linux application cannot cross-compile from macOS (built natively on Linux, 2026-09-19)

Cross-building `bash packaging/linux/deb.sh` from macOS exits 1 with
`fatal error: 'adwaita.h' not found` and `'gtk/gtk.h' not found`. GTK4/libadwaita
development headers for the target are absent, and Homebrew's `gtk4` is a macOS-native
build that cannot supply a Linux sysroot — that part still holds.

**The blocker was removed on a different axis (2026-09-19).** Two additional defects
made the build fail even on a native x86_64 Linux host: the script passed
`-Dtarget=x86_64-linux-gnu` unconditionally (making Zig treat a native build as a
cross-compile and refuse to link system shared libraries), and the icon block plus the
desktop `Icon=` reference were wrong (numbered ImageMagick files, upstream icon id).
Both are fixed (`9daf736e8`, `45e6d086b`), and the **GTK application `.deb` now
builds in WSL Fedora 44 on `kooshapari-desk`**: `khostty_0.1.0_amd64.deb`,
18,143,936 B, `sha256 209ba5ed…713a`, with a size-matched hicolor icon set
(16/24/32/48/256/512) and `Icon=com.khostty.Khostty`.

What remains open is the **install-verify half**: the package has not been installed on
a Linux desktop — no `dpkg -i`, no `desktop-file-validate`, no GUI launch.

What also exists is `khostty-vt_0.1.0_amd64.deb` — the **library** payload, not the
application. It was genuinely installed and exercised: in an x86-64 Debian 12 container,
`dpkg -i` exited 0 (`Status: install ok installed`), `dpkg -V` found no modified files,
`ldconfig -p` resolved the SONAME, the shipped example compiled against the *installed*
headers and `.so` and passed 4/4 VT assertions, and `dpkg -r` removed it cleanly. That
is emulated x86-64 userspace, not bare metal, and not a desktop session.

### 4.4 There is no performance claim

The benchmark harness exists and two paired Khostty/upstream passes were captured
(2026-09-17); `bench/results/README.md` reports them and the raw logs and JSON are
committed beside it. What is still unsupported is any *absolute* performance claim,
for three recorded reasons:

- the upstream baseline was built from a sibling checkout 41 days older than Khostty's
  merge base, so the comparison is directional at best, not same-vintage;
- every pass ran on a heavily loaded machine: the recorded 1-minute load averages are
  **548, 572, 599 and 674** on 10 logical CPUs, and the harness's own README states
  medians moved by more than 3× between a loaded and an idle window;
- the tree was dirty in every pass — the JSON records `git_head` `fc0aea2bc` /
  `d7ec3a36e` with `git_status: dirty` — so the numbers describe no committable
  revision.

**"Khostty is faster than Ghostty" is unsupported.** Reproduce on an idle machine
before citing anything.

### 4.5 The WASM distribution was built from a dirty tree — RESOLVED 2026-09-18

An earlier tarball recorded `source_dirty: yes` at revision `7585c498`, so it could not
be attributed to a clean commit. The dist was **rebuilt from a clean tracked tree**
(`source_dirty: "no"`, commit `7cd94370e`, sha256 `55cfc675…8604dc`), verified by a
54/54 repository suite run, a byte-identical repack, and a 13/13 extracted-tarball
consumer check. No caveat is needed in the announcement for this item.

### 4.6 The IPC surface is spec-complete but not wired into the application

458 module tests pass, including tests that bind real sockets. But `app_host.zig` does
not yet hop to the app's IO thread, the server is not started from the application, and
`pane.write` must become a surface-mailbox message before the terminal may be touched
from a connection thread. `pane.focus` and `pane.search` are `host_unsupported` against
the real runtime. **Nothing is listening in a running Khostty.**

### 4.7 Nothing in this release is published

No git tag, no push, no GitHub release, no crates.io / PyPI / npm / Go-module publish.
The Rust crate, Go module, Python package and npm package all exist as source trees —
none is on a registry. See [RELEASE.md §7](../RELEASE.md).

### 4.8 `go test ./...` does not link on this host today

The WBS G6 row records `go test ./...` → 45 pass. Re-run on 2026-09-18, it **fails at
link**:

```
/usr/local/go/pkg/tool/darwin_arm64/link: running clang failed: exit status 1
ld: multiple errors: tapi error: malformed file
  .../MacOSX27.0.sdk/usr/lib/libresolv.9.tbd:4:20: error: unknown architecture
  arm64e.x1-macos ...
FAIL  github.com/KooshaPari/Khostty/khostty-go [build failed]
```

Apple clang 17.0.0 (clang-1700.3.19.1, Command Line Tools for Xcode 26.0) cannot parse
the `arm64e.x1-macos` token in the MacOSX27.0 SDK `.tbd` stubs. The failure is at link,
after the cgo bindings compile, so the Go source builds; only the recorded test result
is currently unreproducible here. This is a toolchain/SDK mismatch on this host, not a
Khostty source defect, and it does not retroactively invalidate the recorded 45-pass
run — but the figure must not be restated as current until it is re-run on a working
toolchain. **Reported rather than worked around.**
